# AI Shadow Guardian — Endpoint Agent (v0.1, disclosed clipboard DLP)

## What this is

A real Node.js process that:
1. Registers itself as a device against your Convex backend
2. Sends a heartbeat every few seconds so the dashboard's "online" status is genuine
3. Watches the OS clipboard, and when it changes, runs the same secret/PII/source-code
   detection logic the web app's demo simulator uses (`src/convex/dlp.ts`), reporting
   real events to the dashboard when something is flagged
4. Shows a native OS notification on startup and periodically thereafter, disclosing
   that monitoring is active

5. Runs a local network monitor (`network-monitor.mjs`) that detects traffic to
   known AI services (ChatGPT, Claude, Gemini, Perplexity, etc.) once the OS or a
   browser is configured to route through it. Full URL/method/body visibility for
   plain HTTP; domain-only visibility for HTTPS (no TLS decryption). Matches are
   reported the same way as clipboard detections, using each destination's
   configured risk level and action (allow/warn/block) from the dashboard's
   Destinations page — anything not explicitly configured falls back to a
   built-in default list of common AI services.

## What this is NOT (yet)

- No HTTPS content inspection — for encrypted traffic (the vast majority) we see
  *which* AI service was contacted, not the prompt/response content. Seeing that
  too would require generating and installing a trusted root certificate on the
  device to decrypt TLS (a much more invasive step), which this does not do.
- No file-transfer scanning
- No blocking — it only observes and reports, it can't stop a paste, upload, or
  a network request, even one matched to a "block" destination
- No tamper-resistance — a user could kill the process; there's no hardware guardian

Those are larger builds (a TLS-intercepting proxy with an installed root CA for
full HTTPS visibility, a signed/protected service for tamper resistance). This is
a real, working slice, not the whole product.

## Routing traffic through the monitor

The proxy in `network-monitor.mjs` listens on `127.0.0.1:8888` (configurable via
`NETWORK_MONITOR_PORT`) but sees nothing until something is configured to send
its traffic there:

- **Terminal / CLI tools and many apps**: set `HTTP_PROXY` and `HTTPS_PROXY`
  environment variables to `http://127.0.0.1:8888` before launching them.
- **A specific browser, for testing**: set that browser's manual proxy
  configuration (Settings → Network/System → Proxy) to `127.0.0.1:8888` for
  both HTTP and HTTPS.
- **System-wide (all apps on the device)**: set the OS-level proxy —
  Windows: Settings → Network & Internet → Proxy → Manual setup.
  macOS: System Settings → Network → (active connection) → Details → Proxies.
  Both point to `127.0.0.1:8888` for HTTP and HTTPS/Secure.

None of this happens automatically — deciding how (and whether) to force
device-wide traffic through the monitor is a deployment/policy decision, not
something this script does for you.

## Before you run this on any real employee's device

This tool reads clipboard content, which is exactly the kind of monitoring that
requires clear disclosure and, in many places, written policy and consent. Do not
run this on a device without the person using it knowing it's there. At minimum:

- Your organization's acceptable-use / monitoring policy should explicitly mention
  clipboard scanning
- The employee should have acknowledged that policy
- This agent's startup and periodic notifications should never be suppressed —
  if you're tempted to comment out `notifyMonitoringActive()`, stop and reconsider
  the whole deployment instead

## Setup

1. `cd agent`
2. `npm install`
3. `cp .env.example .env` and fill in:
   - `CONVEX_URL` — same value as `VITE_CONVEX_URL` in the main app's `.env.local`
   - `ENROLLMENT_TOKEN` — generated by a manager on the **Employees** page in the
     dashboard, via the "Get enrollment token" button next to a tracked employee.
     It's single-use and expires in 24 hours.
   - `DEVICE_NAME` — whatever you want shown on the dashboard for this device
4. `npm start`

On first run it registers and enrolls the device (consuming the token) and saves
its device ID locally in `.device-state.json` — after that, `ENROLLMENT_TOKEN` is
no longer needed for subsequent runs.

## Running it persistently

For actual use you'd want this running as a background service that restarts on
boot/crash (e.g. via `pm2`, a systemd service, or Windows Task Scheduler), rather
than a terminal window you have to keep open. That's a reasonable next step once
you've confirmed the basic flow works — ask if you want help setting that up for
your specific OS.
